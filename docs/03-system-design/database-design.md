# GymGenius v3

# Database Design

**Version:** 3.0

---

# 1. Overview

GymGenius v3 adopts a **100% Local-First database architecture** built on Hive.

The database is the persistence layer that enables every intelligent decision made by the application.

Unlike traditional fitness applications, GymGenius does not depend on a remote backend to operate. Every critical feature—including workout generation, progress tracking, recovery analysis, and adaptive programming—must remain fully functional without an internet connection.

Cloud synchronization is considered an optional enhancement rather than a system dependency.

---

# 2. Database Philosophy

The database architecture follows six fundamental principles.

---

## 2.1 Local-First

All user information is stored locally on the device.

The local database is always considered the primary source of truth.

No internet connection is required for normal application usage.

---

## 2.2 Domain-Driven Organization

Data is organized according to business domains rather than application screens.

Examples include:

- User Profile
- Workout
- Recovery
- Nutrition
- Progress
- Decision System
- AI Layer

Each domain owns its own persistence model.

---

## 2.3 Offline Intelligence

Every AI engine operates on locally available information.

This includes:

- Workout Engine
- Recovery Engine
- Nutrition Engine
- Progress Engine
- Decision Engine

The database therefore acts as the memory layer of the intelligence system.

---

## 2.4 Historical Integrity

Historical records are never modified.

Workout history, recovery logs and progress data represent the user's long-term fitness journey and must remain immutable.

New information is always appended instead of replacing previous records.

---

## 2.5 Explainability

Every adaptive decision should be traceable.

Whenever the system changes training intensity, exercise selection or nutrition recommendations, the underlying data must be recoverable from the database.

This principle enables Explainable AI.

---

## 2.6 Long-Term Evolution

The database must evolve without invalidating historical user data.

Schema evolution, migrations and versioning are considered first-class architectural concerns.

---

# 3. Storage Architecture

GymGenius uses Hive as its embedded object database.

The storage architecture is intentionally simple.

```text
Flutter Application
        │
        ▼
Repository Layer
        │
        ▼
Hive Database
        │
        ├── User Domain
        ├── Workout Domain
        ├── Recovery Domain
        ├── Nutrition Domain
        ├── Progress Domain
        ├── Decision Domain
        └── AI Domain
```

The Repository Layer isolates business logic from database implementation details.

No engine communicates directly with Hive.

# 5. Core Data Models

The following entities form the foundation of the database.

---

## User

Represents the permanent user profile.

```text
User
├── id
├── personal information
├── fitness goal
├── experience level
├── preferences
├── onboarding profile
└── timestamps
```

---

## WeeklyWorkout

Represents the active workout program.

Unlike daily workout plans, GymGenius stores an entire weekly training schedule.

Example:

Monday
Tuesday
Wednesday
Thursday
Friday

Each training day contains:

- exercises
- sets
- repetitions
- intensity
- progression parameters

The Decision Engine may adjust this weekly workout over time while preserving previous versions inside the workout history.

---

## WorkoutSession

Represents a completed workout.

Stores:

- performed exercises
- actual repetitions
- actual weight
- completion status
- workout duration

Workout sessions are immutable.

---

## RecoverySnapshot

Represents one recovery measurement.

Includes:

- sleep
- soreness
- fatigue
- stress
- recovery score

Snapshots allow the Recovery Engine to identify trends over time.

---

## NutritionProfile

Represents nutritional recommendations for a given period.

Includes:

- calorie target
- protein
- carbohydrates
- fats

Future versions may include micronutrients.

---

## ProgressSnapshot

Represents a summarized view of user progress.

Includes:

- body weight
- strength index
- consistency score
- progression classification

Snapshots are generated periodically by the Progress Engine.

---

## DecisionRecord

Represents every decision produced by the Decision Engine.

Each record stores:

- detected situation
- supporting evidence
- selected action
- confidence
- execution result

Decision history allows complete explainability of adaptive behavior.

# 7. Data Flow Architecture

The database is accessed exclusively through the Repository Layer.

Business engines never communicate directly with Hive.

This architecture guarantees separation of concerns and simplifies future database evolution.

---

## 7.1 Write Flow

Every write operation follows the same pipeline.

```text
UI

↓

ViewModel

↓

Application Service

↓

Repository

↓

Hive Box

↓

Success / Failure
```

Responsibilities:

| Layer | Responsibility |
|---------|----------------|
| UI | Collect user input |
| ViewModel | Manage presentation state |
| Application Service | Coordinate business operations |
| Repository | Validate and persist data |
| Hive | Store objects |

---

## 7.2 Read Flow

Data retrieval follows a similar architecture.

```text
Hive

↓

Repository

↓

Application Service

↓

Business Engine

↓

Decision Engine

↓

AI Layer (Optional)

↓

UI
```

This flow ensures that:

- business rules remain centralized
- engines operate on validated data
- AI never accesses Hive directly

---

## 7.3 Adaptive Decision Flow

Adaptive Programming relies on multiple engines working together.

```text
Workout Session Completed

↓

Workout Logs Updated

↓

Progress Engine

↓

Recovery Engine

↓

Nutrition Engine

↓

Decision Engine

↓

Weekly Workout Updated (if required)

↓

AI Explanation Generated

↓

User Notification
```

Not every decision results in a workout modification.

In many situations the Decision Engine simply decides to:

- keep the current program
- delay progression
- recommend recovery
- adjust nutrition only

# 8. Data Consistency Rules

Maintaining data consistency is critical because every intelligent recommendation depends on historical accuracy.

---

## 8.1 Single Source of Truth

Each piece of information exists only once.

Examples:

- body weight → Weight Logs
- recovery score → Recovery Logs
- weekly workout → Weekly Workout Box

Duplicate storage is avoided whenever possible.

---

## 8.2 Immutable Historical Records

Historical records must never be modified.

Examples include:

- completed workout sessions
- previous weekly workouts
- progress snapshots
- recovery snapshots
- AI decision history

If new information becomes available, a new record is created instead.

---

## 8.3 Derived Data

Derived values are never considered authoritative.

Examples:

- readiness score
- fatigue score
- progression index
- AI confidence

These values can always be recalculated from historical data.

---

## 8.4 Transaction Integrity

Operations involving multiple Hive boxes should be treated as a single logical transaction.

Example:

Workout completed

↓

Save Workout Session

↓

Save Exercise Logs

↓

Update Progress Snapshot

↓

Create Decision Record

↓

Generate AI Explanation

If one step fails, the system must avoid leaving inconsistent state.

---

## 8.5 Engine Ownership

Each Engine owns its own derived data.

| Engine | Owns |
|---------|------|
| Workout Engine | Weekly workout adaptations |
| Recovery Engine | Recovery metrics |
| Nutrition Engine | Nutrition recommendations |
| Progress Engine | Progress indicators |
| Decision Engine | Adaptive decisions |

No Engine modifies another Engine's internal calculations.

---

# 9. Performance Strategy

GymGenius is designed for fast local execution.

Performance optimization is built into the storage architecture.

---

## 9.1 Lazy Loading

Large datasets are loaded only when required.

Examples:

- workout history
- progress history
- recovery history

This minimizes memory consumption.

---

## 9.2 In-Memory Cache

Frequently accessed objects remain cached.

Examples:

- active user
- active weekly workout
- latest recovery snapshot
- current nutrition profile

Cache is refreshed automatically after updates.

---

## 9.3 Batch Writes

Whenever multiple related objects are created, they should be written together.

Examples:

- workout completion
- routine regeneration
- weekly evaluation

Batch operations reduce disk overhead.

---

## 9.4 Archive Strategy

Historical data should remain accessible while minimizing memory usage.

Examples:

- recent sessions → loaded immediately

- old sessions → loaded on demand

---

## 9.5 Scalability

The architecture is designed to support years of continuous usage.

Expected datasets include:

- thousands of workout sessions
- thousands of exercise logs
- hundreds of progress snapshots
- hundreds of recovery records

Performance should remain stable throughout the application's lifetime.

---

# 10. Security Strategy

GymGenius is Local-First, but local data must still be protected.

---

## 10.1 Repository Validation

Every database write must pass through the Repository Layer.

Repositories validate:

- required fields
- object integrity
- domain constraints

Invalid data must never reach Hive.

---

## 10.2 Data Integrity

Each persisted object should contain:

- unique identifier
- creation timestamp
- optional update timestamp
- schema version

This supports future migrations.

---

## 10.3 Future Encryption

Future versions may encrypt sensitive information.

Possible candidates:

- authentication credentials
- personal profile
- health information

Encryption should remain transparent to business logic.

---

## 10.4 Local Privacy

GymGenius prioritizes user privacy.

Personal information is never transmitted unless the user explicitly enables optional cloud synchronization.

The application should always function without external services.

---

# 11. Schema Evolution Strategy

The database is expected to evolve continuously.

Schema evolution must never compromise user history.

---

## 11.1 Backward Compatibility

Older databases should remain readable after application updates.

Breaking changes should be avoided whenever possible.

---

## 11.2 Versioned Models

Every persistent entity should include:

- Hive TypeId
- schema version
- migration strategy

Example:

```text
WorkoutPlan

Schema Version 1

↓

Schema Version 2

↓

Automatic Migration
```

---

## 11.3 Historical Preservation

Historical data is never rewritten.

Instead:

- preserve original records
- create transformed representations
- rebuild derived values when needed

Historical information remains the ultimate source of truth.

---

# 12. Migration Strategy

Database migrations occur automatically during application startup.

The migration process is fully transparent to the user.

---

## Startup Pipeline

```text
Application Launch

↓

Open Hive

↓

Read Database Version

↓

Compare Versions

↓

Migration Required?

↓

Execute Migration

↓

Validate Data

↓

Continue Startup
```

The application becomes available only after successful migration.

---

## Supported Migration Types

GymGenius supports several migration categories.

### Model Evolution

Examples:

- new optional fields
- renamed properties
- improved structures

---

### Data Transformation

Examples:

- rebuild progress metrics
- convert workout formats
- update decision records

---

### New Hive Boxes

Examples:

- Wearable Data
- Health Snapshots
- Coach Conversations
- AI Cache

---

### Deprecated Boxes

Deprecated boxes are never removed immediately.

Lifecycle:

```text
Migrate Data

↓

Validate

↓

Archive

↓

Remove in Future Version
```

This approach guarantees maximum safety during long-term application evolution.

# 13. Database Versioning

GymGenius separates **application versioning** from **database schema versioning**.

This allows the application to evolve without forcing unnecessary database changes.

---

## 13.1 Version Mapping

| Application Version | Database Version |
|---------------------|-----------------:|
| 3.0.0 | 1 |
| 3.1.0 | 2 |
| 3.2.0 | 3 |
| 4.0.0 | 5 |

Database versions increase only when the persistence layer changes.

---

## 13.2 Semantic Versioning

The application follows Semantic Versioning.

- Major → Breaking architectural changes
- Minor → New features
- Patch → Bug fixes

Database versions evolve independently.

---

## 13.3 Model Versioning

Every persistent entity should expose:

- Hive TypeId
- Schema Version
- Created At
- Updated At (optional)

Example:

```text
WeeklyWorkout

TypeId: 12

Schema Version: 3
```

This simplifies future migrations and debugging.

---

# 14. Migration Validation

Every migration must be validated before the application becomes operational.

Validation ensures that migrated data remains usable and consistent.

---

## Validation Checklist

The migration framework verifies:

- object integrity
- required fields
- duplicated identifiers
- invalid references
- corrupted objects
- incompatible schema versions

---

## Integrity Rules

The following conditions must always be satisfied:

- every Workout Session belongs to one Weekly Workout
- every Decision Record references an existing user
- every Progress Snapshot has a valid timestamp
- orphaned records are rejected

---

## Validation Outcome

```text
Migration

↓

Validation

↓

Passed?

↓

YES → Continue Startup

NO → Execute Recovery Strategy
```

---

# 15. Rollback Strategy

Whenever possible, database migrations should support rollback.

Rollback minimizes the risk of permanent data loss.

---

## Safe Migration Pipeline

```text
Backup Current Database

↓

Execute Migration

↓

Validate Data

↓

Migration Successful?

↓

YES

↓

Replace Previous Version

↓

NO

↓

Restore Backup
```

---

## Backup Policy

Before major migrations:

- preserve existing Hive boxes
- create temporary backup
- validate migrated objects
- delete backup only after success

---

## Failure Recovery

If migration fails:

- preserve original data
- generate diagnostic logs
- notify the user
- prevent corrupted startup

The user's historical data must never be sacrificed.

---

# 17. Cloud Synchronization Strategy

Although GymGenius is Local-First, optional cloud synchronization may be introduced in future versions.

Cloud synchronization must never become mandatory.

---

## Synchronization Principles

The local database always remains the primary source of truth.

Cloud services act as:

- backup
- synchronization layer
- multi-device support

They never replace Hive.

---

## Synchronization Flow

```text
Hive

↓

Synchronization Service

↓

Conflict Resolution

↓

Cloud Storage
```

---

## Conflict Resolution

If conflicts occur:

Priority order:

1. Valid Local Data
2. Most Recent Valid State
3. User Confirmation (if required)

Automatic conflict resolution should remain deterministic whenever possible.

---

## Offline Guarantee

Loss of internet connectivity must never interrupt:

- workout tracking
- adaptive programming
- recovery analysis
- nutrition recommendations
- AI explanations (Local Mode)

The application always remains fully operational.
